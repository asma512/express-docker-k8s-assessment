Production deployment should start with a small, repeatable container build and a clear separation between application code and runtime configuration. The preferred workflow is to build the Express API locally or in CI, push the image to Amazon Elastic Container Registry (ECR), and then deploy that immutable image into the target cluster. The same pattern applies to the React client, which can be built as a static artifact and served through Nginx. For AWS, the typical path is to store the image in ECR, create or update the Kubernetes deployment, and let the cluster pull the image from the registry using a secure IAM or workload identity mechanism.

For this project, I would choose Amazon EKS as the primary deployment target because it scales better for production workloads, supports multi-replica deployments, and fits the assignment’s focus on orchestration and cloud-native deployment. EC2 with Docker Compose is simpler and cheaper for a single-stack deployment, especially for small internal applications, but it requires more manual operational work, has weaker elastic scaling, and provides less robust orchestration features than EKS. Docker Compose on EC2 is useful for rapid proof-of-concept deployments or low-traffic systems, while EKS is a stronger choice when the application needs resilience, rolling updates, autoscaling, and easier future growth.

Secrets should never be committed to the repository. In production, runtime values such as JWT secrets, database credentials, and cloud access settings should be injected using AWS Secrets Manager or AWS Systems Manager Parameter Store, then mounted as environment variables or Kubernetes Secrets. This keeps configuration out of source control and allows rotation without rebuilding the image.

The scaling strategy should be workload-driven. Horizontal scaling is best when traffic rises but the application remains CPU- or latency-bound, such as when more API replicas are needed behind a load balancer. Vertical scaling is appropriate for smaller systems where a single instance is nearing memory or CPU limits or the workload is not yet distributed enough to justify more replicas. In practice, a production deployment often begins with a modest number of replicas and then scales horizontally when traffic grows beyond the node capacity.

Cost control is critical. The main AWS resources for this architecture would include ECR for image storage, EKS control plane and worker nodes, an Application Load Balancer or NodePort-based access pattern depending on the design, Elastic Block Store for persistent data, and optionally MongoDB Atlas or a managed MongoDB service to avoid running a database cluster manually. To minimize cost, keep the cluster small, use right-sized node groups, enable autoscaling, avoid over-provisioning resources, and store only the required image layers in ECR. A managed database and autoscaling worker nodes reduce operational overhead while providing enough flexibility for production growth.
